## 1. 产品目标与范围

用户通过自然语言，在已有项目中生成或修改图片 Prompt、分镜 Prompt。助手跨章节记住有明确范围的创作约束，每个实际生成请求包含独立完整的提示词。用户无需复制粘贴或手工修正文案。

产品 Agent 只有两类业务写工具：`update_image_prompt`、`update_storyboard_prompt`。允许受限读取上下文，允许内部保存会话和用户明确表达的创作约束。内部分镜段落的编辑属于分镜 Prompt，不涉及业务 Scene 的增删。

不开放：书稿改写、项目配置变更、资产身份或引用关系变更、资产/变体创建删除、Scene 新增删除重排、数字人和音频操作、图片/视频生成、媒体删除、导出发布、任意 HTTP/SQL/文件或命令执行。既有生成按钮继续由用户使用。

助手可以解释全流程和读取相关状态，但不能执行超出上述范围的操作。请求范围明确时直接修改，展示差异并允许撤销；不增加逐条审批弹窗。目标或约束范围有实质歧义时才澄清。

## 2. 开发规范与 Ponytail

遵循仓库 AGENTS.md，并采用 [Ponytail 主技能](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/skills/ponytail/SKILL.md) 的简化原则。参考版本：`2ed6c52c9d7e5e56942508591085fd45dea277d3`；只引用规范，不要求安装其插件或生命周期 hooks。

对本项目的执行要求：先追踪调用链和查找可复用对象，再决定新增代码；标准库、平台和已安装依赖能够解决的事情，不增加新依赖；无实际职责边界时不新增接口、工厂、代理层或通用框架；业务必须覆盖的校验、数据保护和可访问性不得精简掉。复杂性审查是正确性审查的补充。[Ponytail review](https://github.com/DietrichGebert/ponytail/blob/2ed6c52c9d7e5e56942508591085fd45dea277d3/skills/ponytail-review/SKILL.md)

适用规则明确如下：

- 项目要求的 pytest/Vitest 回归、类型检查、构建及旧库兼容测试必须保留；Ponytail 的最小测试建议不能降低这些要求。
- 项目要求模块化 OOD，但类必须有独立职责或替换/测试价值。纯格式化使用函数；不为单个实现建立 AbstractRepository、AgentFactory 或第二套事件系统。
- API 处理协议及权限入口，Controller 编排，Service 承担上下文、工具业务及持久化；不把全部实现塞进 Controller，也不机械地为每一步新增一个类。
- Vue 组件采用 Composition API、`script setup lang="ts"`，TypeScript strict/noUnused 检查通过；禁止无说明的 `any`。
- 所有 Agent 指令、语言规则与输出模板集中在 `prompts/`。模板渲染无数据库、网络与持久化副作用。
- 每阶段先补暴露问题的回归，再做最小根因修复；不得按供应商名称散落特例。
- 不删除兼容代码、种子或画布核心；不修改密钥文件、CI/CD；不覆盖无关修改。提交使用项目约定格式，执行前检查实际分支，不自动切换有用户修改的工作区。

## 4. 独立生成单元与输出合同

### 4.1 三种序号不能混用

1. `Chapter.number`：章节顺序。
2. `Scene.sequence`：章节内业务分镜顺序，不由 Agent 修改。
3. Prompt 内小镜头序号：一次生成请求内的局部编号，每个请求从 1 开始，由渲染器按有序列表生成。

保留现有“一条 Scene 对应一个生成请求”的关系。默认单镜头 Prompt 仍使用现有结构。用户明确要求 A、B 各包含三个内部小镜头时，在同一 Scene 的 Prompt 参数中保存内部段落列表，分别渲染 1、2、3；不创建六条 Scene，不把章节续写的 `next_sequence` 传给内部编号。

内部段落没有可由模型填写的序号字段。模型生成主体、动作、景别与时间内容，列表顺序就是顺序；固定总时长及已有台词/旁白绑定不得被无关修改悄悄改变。允许的结构增量在 P0 冻结，以扩展现有 `prompt_params` 为优先，不新增内镜头业务表。

### 4.2 自包含边界

最终请求由当前单元的公共角色/场景描述和各内部段落组成。允许内部段落使用当前请求已经完整定义的 `@{角色名}`；禁止依赖其他 Scene 才能解释的“镜头1的女生”“衣服同上”“其余照旧”。

若下游实际把内部段落拆成多个独立请求，每个请求必须重新携带公共定义。参考图、实体标识和服装版本来自当前有效资产，不让模型猜测。引用缺失不能用臆造身份或创建新资产补齐。

自包含校验包括结构、已解析实体、必需描述及跨单元依赖。不得只用关键词正则：对白中的“和上一回一样”等正常叙事不能被机械禁止。对无法程序证明的语义一致性通过评测核验，不能承诺百分之百自动判定。

### 4.3 更新合同

- `update_image_prompt`：目标为已存在的 Asset 或 AssetVariant，只修改该对象 `base_traits`。身份、变体适用范围、图片和引用关系只读。
- `update_storyboard_prompt`：目标为已存在的 Scene，接受允许字段的结构化局部修改。服务端以当前对象合并，再调用共享渲染器生成最终 `prompt`，原子保存相关 `prompt_params`。无关 `description`、时长、配音、素材、状态等保持不变；确需同步摘要等派生字段时在 P0 列入明确白名单。
- 两个工具均支持空 Prompt 首次填充、单对象和授权范围内批量；不开放通用字典 Patch 或任意字段路径。
- 历史纯文本 Prompt 必须可编辑：保留原文作为修改依据，不凭空补全不存在的结构参数。已有结构与手工文本不一致时以最新可验证内容为准，标记需要重建的派生内容，不将旧参数覆盖回来。兼容规则先写回归再修改共享保存入口。

## 5. 上下文与创作约束

### 5.1 数据来源

项目摘要、角色/场景事实、变体适用章节来自业务数据库。用户明确建立的创作限制单独保存；近期对话用于理解“第二个”“再冷一点”等指代。模型的推断不得自动升级为锁定设定。

每条约束至少包含：项目/团队范围、内容、作用目标或明确剧情区间、来源用户消息、状态与版本。能够复用 AssetVariant.chapter_numbers 的服装适用信息直接读取，不再维护第二份服装表。

作用范围分为项目、章节、已有场景/目标集合、当前 Scene、角色/变体相关目标。场景没有独立业务 ID 时保存已确认的目标集合或边界；不只保存“这场戏”字符串。剧情区间按书中顺序计算，不能按用户的编辑时间推断。

### 5.2 传播与冲突

- “这个镜头用暖光”：只修改当前 Scene，不创建全局约束。
- “这场戏都用暖光”：范围可解析时保存场景约束；用户明确要求修改的已有目标一并更新。
- “以后男主穿这件外套，直到回家”：将服装约束绑定到明确剧情起止范围；终点无法解析时澄清，禁止猜测后续章节范围。
- “试试红色外套”：当前目标的可撤销尝试，不晋升为长期身份设定。
- 约束冲突优先遵循明确的用户替代关系与有效范围；锁定设定不能被隐式覆盖。范围外的规则不参与当前请求。
- 新约束默认影响后续相关修改/首次填充，不自动批量重写所有既有 Prompt。对受影响的已有内容给出待更新提示；“把本章都改过来”才构成批量授权。
- 用户单纯要求“记住”时可记录受限创作约束；这属于会话处理，不增加第三种业务写工具。持久化前校验消息来源、范围和冲突，不允许模型写入权限或系统规则。

### 5.3 每轮构建

必需约束和相关实体通过 ID、章节及区间确定性加载；历史对话只取必要窗口/摘要。摘要不能替代关键约束原记录。A 的全量 Prompt 不默认附加给 B；连续性整理成 B 的当前人物、位置、物品和情绪状态。

无需向量数据库、知识图谱或多 Agent。先用数据库范围过滤；预算超限优先裁剪无关历史，不能静默丢掉硬性约束。即使页面切换或新建对话，仍可读取同一项目的有效约束。不同用户私有对话不可因同项目而自动互相暴露。

## 6. 最小后端与存储边界

建议在 `services/creation_agent/` 内放置运行编排、上下文准备、两个工具的业务实现；`schemas/creation_agent.py` 定义合同，`prompts/creation_agent.py` 保存指令。实际文件数量由职责和复用决定，不为遵循目录示例强制拆文件。

复用 `AiTask` 标识一次用户请求的运行与用量关联，不新增 Agent 队列或另一套运行状态库。会话、消息、约束和改动记录是新增持久化职责，优先放在一个模型模块中定义必要实体：

| 数据 | 最小用途 |
| --- | --- |
| Conversation | 项目、团队、会话所有者与摘要/摘要版本 |
| Message | 按会话顺序追加的用户/助手消息及完整工具结果；支持分页，不持续重写整部小说的聊天 JSON |
| Constraint | 有来源、有适用范围、有版本的创作限制 |
| PromptChange | AiTask、工具调用 ID、目标、修改前后值、版本/冲突信息及撤销关联 |

由 AiTask.request_params/response_data 关联 conversation、message、scope snapshot 和用量；字段扩展必须通过 schema 约束。不要将供应商密钥复制到这些记录。消息持久化使用 Pydantic AI 官方序列化方式，不自定义另一套模型消息协议。

运行接入采用官方 AG-UI 适配与 JS 客户端。AG-UI 只承载运行事件；普通查询、差异和撤销遵循现有 REST 响应结构。服务端从可信会话恢复历史，只接受新用户输入和经验证的选择，不信任客户端传入的 system、工具结果、租户 ID 或任意前端工具。

一次会话只运行一个写请求；多个会话命中相同目标时通过数据库原子版本检查保护。工具写入与改动记录同一事务，同一调用重复提交返回原结果。批量工具调用内要么全部提交要么不提交；一个运行的前面工具已经提交而后面失败时，必须列出已提交操作，不能报告“什么都没改”。

撤销通过应用的受限 REST 操作执行，只恢复该次修改字段，检查目标后续版本；不让 Agent获得通用回滚工具。用户要求撤销且存在冲突时展示冲突，不覆盖后续手工或其他会话修改。

断开 SSE 不等于取消任务。显式停止写入取消标记，模型调用返回后及每次写前再次检查；已提交操作保留并展示。服务重启后从 AiTask/改动记录恢复真实状态，不能盲目重放工具。先复用现有执行器并验证其启动恢复行为，不新增通用调度框架。

## 7. 模型、费用与配置

按现有团队/项目模型解析路径选择模型，工具调用能力独立于 supports_json_output；不支持时给出明确错误，不静默切供应商。版本组合在 P0 验证后锁定，不直接照搬官网 latest。

每轮限制模型请求数、工具调用数、批量目标数、上下文预算、输出和运行超时；这些运行能力与开关来自后台配置。模型只为需要判断的内容工作，编号、完整描述展开和可确定校验使用程序完成；不固定增加审核 Agent 或第二次模型审查。

每次真实模型请求记录用量并归集到 AiTask，包括重试、摘要、失败和取消后的已消费请求。继续由既有 billing/pricing 路径计算价格和扣费；不可同时由新 Agent 和旧执行器重复记录。供应商缺失用量时明确标记不可计量/估算状态，不伪造零成本或未经依据补扣。

## 8. UI 与组件设计

一个共享 `CreationAgentPanel`，一个必要的 `PromptChangeCard`，一个会话状态/AG-UI 适配位置即可起步；消息气泡、输入、列表用 Element Plus X。不要再写一套 AIMessage/AIButton/AIDrawer 基础库，也不改造全站为 Element Plus 风格。

复用现有主题 `--app-*`、字体和 lucide 图标。在助手容器范围内把 Element Plus 的色彩变量映射到现有主题；按需导入，不引入全局 reset。画布独立主题通过已有 themeScope 判定适配，不能靠新增一组全局覆盖修补。弹出层沿用项目 Teleport/层级方式，映射相同主题，避免脱离容器后变色。

用户确认的交互（2026-09-04补充）：桌面使用Flex右侧分栏，助手占独立宽度，打开时主页面收窄、关闭后恢复，不悬浮遮挡页面。分镜布局按工作区实际可用宽度响应。顶部显示“当前章 / 当前镜头或选中数量”，中间消息，底部输入和停止。改动卡显示保存状态、涉及对象、展开差异、定位和撤销。Prompt 详情默认折叠，普通用户不必编辑或理解内部字段。

窄屏无法容纳两栏时，将助手作为独立工作区显示，暂时隐藏主内容但保留组件与草稿；关闭后恢复主内容。顶部导航仍可访问，助手不使用模态语义或焦点陷阱。面板在页面切换后恢复会话；请求发出时冻结目标集合，切换选择不能改变正在执行的范围。空状态、读取中、执行中、已保存、失败、取消、已修改部分目标和冲突必须可区分；成功依据工具提交结果，不依据模型话术。

验收浅色、深色和画布主题；1440×900、1280×720、390×844；键盘打开/关闭、焦点归还、中文输入法组合态、重复提交保护、滚动阅读旧消息和无障碍名称。达到 WCAG AA 基本对比度，200% 缩放可操作。只展示实际动作摘要，不展示模型私有思考链。

## 9. 必须在实现前明确的审核项

以下标记“需人工审核”，依据仓库 AGENTS.md；当前只是方案，不代表已获实现批准：

- 权限：Conversation 私有历史、项目约束共享范围、管理员/创作者/只读角色以及每个工具目标校验复用方案。
- 数据库：新增表、可能增加的模型能力/版本字段、SQLite 旧库兼容及配置的其他数据库更新路径；不得删除数据，回退代码保留新表。
- 计费：AiTask 归集、失败/重试/摘要用量、扣费幂等、余额不足和供应商用量缺失行为。
- 依赖：计划采用的新增包、准确版本、传递依赖和锁文件差异；按项目要求在明确授权后变更，不顺带升级既有依赖。

阶段内可先完成不触及以上边界的离线合同、回归及可审查设计，再提交具体差异方案；不以笼统风险为由暂停整个计划。上线使用后台开关，关闭后既有创作入口可继续工作，保留会话和改动记录。
