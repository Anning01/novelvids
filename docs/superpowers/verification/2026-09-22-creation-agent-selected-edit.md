# 选中分镜后的追问与人物引用修复

## 现场证据

最新失败请求已经携带 `write_scope=selected` 和一个分镜目标，前端没有丢失选择。模型第一步却只请求目录与项目资料，没读取选中对象；随后尝试读取 9 个对象，超过单批上限，再分批读取全章并回查压缩档案。6 次请求中包含 1 次摘要、5 次主请求，没有执行保存。最后一次仍调用已收起的读取工具，界面显示了泛化的执行失败。

另一个独立问题是默认分镜渲染器和历史文本编辑路径会自动展开人物定义，仅删除提示词中的人物描述会被重新补回。

## 修改

- 每轮模型请求末尾附带本轮章节、操作范围和选中目标的轻量快照，不附带全量正文。历史选择不能覆盖新选择。
- 获取上下文默认读取已选目标；目录仍按需读取。提示词明确“帮我改”“继续”只作用于本轮选中对象，长期规则范围不等于本轮批量操作范围。
- 读取工具向模型显式声明单批对象上限，后端既有检查继续有效。
- 分镜增加可持久保存的 `reference_only_types` 渲染选项。设为 `人物` 时保留人物引用和关联，移除系统生成的人物外貌定义；其他类型仍按原规则渲染。支持结构化分镜与历史文本，后续修改不会重新补回排除的定义，也可通过清空选项恢复默认行为。
- 精确处理系统生成的引用栏目，不删除正文中的人物动作、台词、声音或其他资产描述。不改写其他分镜，保留原有版本检查与撤销机制。
- 最后一次回复阶段调用已收起工具而触发重试错误时，显示调用额度说明；真正的连接错误仍显示模型故障提示。

## 验证

- 相关 API、Agent、分镜、提取、参考图回归通过；定向覆盖了当前选择与旧全章要求冲突、隐式追问、旧文本/结构化渲染、人物关联、动作对白保留、其他类型保留、后续编辑、恢复默认以及撤销。
- 真实模型通过正式任务链路复现：历史要求“人物提示词不要放进镜头”，选中一个分镜，再发送“帮我改啊”。3 次模型请求、18,737 输入 token，成功保存且只改选中分镜；第二个分镜保持原样。
- 真实测试只使用内存业务数据，没有替用户重放生产会话。此次费用按现有配置估算 ¥0.241140；累计 ¥9.348938，剩余 ¥0.651062，无未结清请求，仍在 ¥10 预算内。
