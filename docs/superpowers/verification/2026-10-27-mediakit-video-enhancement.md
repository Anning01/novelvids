# AI MediaKit 成片画质增强：执行与验收

日期：2026-10-27。状态：本地实施与工程验收完成，三次真实增强已保存，用户已接受双人物样例效果；未合并、推送或部署。原矩阵保留为验收合同，实际覆盖范围和限制以下方记录为准。范围与合同以[开发计划](../plans/2026-10-27-mediakit-video-enhancement.md)为准，范围变化先更新计划。

本文件用于逐阶段执行、收集证据和决定能否交付。现有生成链路的历史测试与刚完成的生产部署，不计作本功能的测试通过。

## 1. 执行顺序与记录规则

1. 阅读根目录 `AGENTS.md`，记录当前分支、提交、工作区修改和依赖状态；检查计划列出的实际调用方。代码开发才从最新 `develop` 建立计划中的分支，不覆盖其他工作。
2. 完成 P0 合同与 H1–H4 人工审核，记录官方未明确事项的工单/资料结论；在隔离样例上先写失败回归。不提前启用收费工具。
3. 按 P1 → P2 → P3 实施，每阶段记录改动文件、复用对象、检查命令、验收 ID、证据及未完成项。新接口、schema、调用方、前后端错误展示必须同步。
4. 离线合同、真实 PostgreSQL/SQLite 的隔离测试、真实供应商测试分开记录。真实任务异常保留，不能删除失败或改预期掩盖问题。
5. P4 前填写并获准预算，核对 Key 的服务权限、账号余额和输入访问条件；预算未批准时只完成准备和离线验证，不提交收费任务。
6. 完成全部阻断用例后审阅差异、运行提交检查，整理 PR；合并、上线及任何生产数据维护另行授权。

结果只能填写“未执行 / 通过 / 失败 / 阻塞 / 按规定跳过”。通过必须附提交、环境、命令或操作与证据位置；“看起来可用”“模型说已完成”不算证据。本文所有 G、D、A、T、C、U、R 编号唯一，引用时必须逐项确认，不能一次勾选整组。

### T：任务、并发与恢复

| ID | 场景 | 通过标准 |
| --- | --- | --- |
| T01 | 双击、并发和刷新 | 同请求 ID 双进程并发只产生一个逻辑操作；不同成员/请求 ID 对同一来源/配方也复用，费用只归属首次实际提交者且私有聊天不泄漏；相同 ID 不同参数稳定冲突；刷新/重开返回原任务 |
| T02 | 提交响应丢失 | 覆盖发出前、已接受未回包、有编号未保存三处中断；只在已验证的供应商幂等条件内复用原 token，不能换 token 试探；无法确定则待核对 |
| T03 | 处理中及重启 | 供应商返回 success 但仍 running 时不显示完成；查询 429/5xx 退避；重启使用原编号查询，重复 worker 不重复提交，无连续 LLM 等待 |
| T04 | 下载/转存失败 | 供应商完成但下载超时、上传中断或进程崩溃，只恢复文件保存；供应商提交次数保持一；未持久化成功不能显示可下载高清版 |
| T05 | 链接过期/任务过期 | 固定结果有效期与任务查询范围分别处理；不可恢复时记录实际状态、原片及费用，不自动再增强，不把查询当作续期 |
| T06 | 取消 | 提交前取消零供应商调用；提交后取消停止后续发布但继续按已知能力收集结果/费用，界面不虚报供应商已取消或免单 |
| T07 | 损坏结果和错误内容 | 非视频、截断、错误宽高、帧率/时长不符、丢音轨/音画错位不记成高清导出成功；保留诊断与原片，恢复保存不触发新生成 |
| T08 | 恢复、回退与待核对 | 人工收口有证据与操作者；旧收口不能覆盖迟到新证据；停用新提交后仍能收集已接受任务；代码回退不删除新增审计或盲目重放 |

## 4. 自动化检查命令

```bash

AUTH_ENABLED=false uv run pytest test/test_services/test_video_enhancement*.py test/test_services/test_chapter_exports.py -q --no-cov

# 前端定向回归：新增组件与现有调用方测试共同运行。
cd web
npm run test -- src/features/video-export
npm run typecheck
npm run build
```

提交前在仓库根目录运行后端全量 `AUTH_ENABLED=false uv run pytest`、权限全量 `AUTH_ENABLED=true uv run pytest test/test_auth -q --no-cov`；在 `web/` 运行前端全量 `npm run test`、类型检查与生产构建，最后 `git diff --check`。失败有实际原因和修复证据，不能删除/跳过测试掩盖。

新增业务可度量部分定向覆盖率目标≥80%，显式把新增 services 纳入覆盖范围；重点看提交/保存/结算故障分支，不靠只测字段赋值提高数字。并发与数据库测试须另附实际 SQLite/PostgreSQL 版本、双进程日志与初始化/重复启动结果，不能以 SQLite 替身声称 PostgreSQL 通过。

真实测试只可按仓库规则因缺少 `test/.test.env` 跳过。配置存在但预算未批准属于“阻塞”，不是改写或绕过测试的理由；不得运行可能付费的完整测试集。预算批准后，以审核过的真实用例范围运行并记录所有实际结果。

### 5.2 固定样例和逐步操作

1. 选用两章各约30秒的已有合法 480p 片段，包含人物近景、老人/少年、快速动作、衣物细节、暗场及文字/道具，覆盖对白和旁白。记录每个素材的摘要、探测信息与是否有原生1080p对照，不为凑齐样例自动生成。
2. 页面准备不可变成片，核对采用镜头与版本、顺序、比例、原片实长和全部声音；下载原片并记录摘要。来源发生变化先重新准备，不能沿用旧确认。
3. 查看1080p、原帧率的费用与来源卡片，明确执行一次。记录内部任务、导出 ID、供应商任务号、稳定 token 的脱敏摘要和提交次数；不在截图/日志保留 Key、签名查询参数或私有素材 URL。
4. 保持一个任务运行时关闭页面，再打开并恢复；在受控测试环境重启服务，验证后台只查询已有供应商编号。生产环境不为测试重启。
5. 完成后下载高清文件，核对长期存储引用与文件探测；两次刷新/重复下载/重复请求后验证供应商提交数、导出数和流水不增加。
6. 由验收人完成 R02/R03，登记评审者、原片与增强版并排截图、关键时间点及评分理由。截图只说明静帧，时间稳定性与音画同步必须实际播放检查，不能只用模型自评分宣布通过。
7. 核对实际输出时长、帧率、价格快照、费用、耗时及供应商账单可查状态；尚未出账时只能标“用量估算已核对，最终账单待核对”。
8. 汇总所有成功和失败尝试。质量不达标、音画异常、金额矛盾或预算接近上限时停止新提交，保留证据；修复后先做离线回归，再为额外真实调用另获授权。
