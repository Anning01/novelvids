# 项目名称的归属范围与旧库迁移

项目 ID 标识项目。名称只在所属范围内去重，不能作为全站唯一标识：

| 项目归属 | 名称范围 |
| --- | --- |
| 有 `team_id` | 同一团队；不同成员共享该范围 |
| 没有团队，有 `created_by` | 同一创建者 |
| 两者都没有 | 关闭登录时的共享本地工作区 |

不同团队、不同个人范围允许使用完全相同的名称。启用登录时，只有既无团队也无创建者的历史项目会回填到默认团队；已有创建者的个人项目在重复启动后仍保持个人归属。剧本导入和人工创建在本范围重名时添加 ` (2)`、` (3)` 等编号，长标题会为编号预留长度。已有项目和书稿名称不改动。重制项目和手动改名继续按既有规则报告本范围内的重名冲突。数据库唯一索引约束所有写入路径，并发请求也不能绕过约束。查询、修改和删除仍由原团队权限检查，知道同名项目不能越权访问。

## 需人工审核：旧库迁移

新安装通过模型创建 `uid_novels_scope_name` 范围唯一索引。旧安装仍可能包含 `novels.name` 的全局唯一约束；`generate_schemas(safe=True)` 不会移除它。**迁移不会在启动时自动执行。** 先审查并执行迁移，再进行跨团队同名验收。

只读预览，使用现有 `DATABASE_URL`，不打印名称、正文或连接凭据：

```bash
uv run --no-sync python scripts/migrate_project_names.py
```

SQLite 操作流程：

1. 暂停后端，避免备份后产生新的写入；保留当前代码版本。
2. 执行以下命令。`--backup` 必须指向一个不存在的文件，不能覆盖已有恢复点。备份使用 SQLite backup API，包含已提交的 WAL 数据，文件权限为 `0600`。
3. 启动后端，检查项目列表、章节和团队隔离；不同团队各创建一次同名项目。

```bash
uv run --no-sync python scripts/migrate_project_names.py --apply \
  --backup data/novelvids-before-project-name-scoping.db
```

SQLite 不能直接删除内联 UNIQUE。迁移在一个写事务中复制原表结构及数据到临时表，只去掉名称的全局唯一约束，再替换回原表名。保留所有列、项目 ID、正文、额外字段、其他唯一约束、索引、触发器、视图引用及自增高水位。外键检查不能新增违规记录；失败回滚整个事务，恢复原外键及 ALTER TABLE 设置。未知旧表定义会拒绝执行，要求人工审查。重复执行不重建已迁移的表。

恢复：停止后端后，用此次备份恢复原数据库和对应代码版本；需要一并处理原数据库的 WAL/SHM，确保没有仍持有旧连接的进程。**迁移后若已产生新项目，不要直接覆盖数据库**，先保存新数据并人工处理同名记录，再制定恢复方案。旧代码依赖全局唯一名称，不能只切回旧代码而保留跨团队同名的新数据。

PostgreSQL 需先由管理员创建数据库备份或快照，再停止写入并运行相同脚本的 `--apply`。脚本在事务内先建立范围唯一索引，再根据系统目录中的实际名称移除旧全局约束及独立索引。不会猜测约束名或使用 CASCADE。当前覆盖 SQL 调用契约测试，真实 PostgreSQL 实例验收另行记录。

实现：`models/_project_name_index.py`、`controllers/novel.py`、`services/project_name_migration.py`、`scripts/migrate_project_names.py`。回归覆盖范围隔离、并发与重制写入，以及旧库迁移、重复执行、备份保护、关联保留和故障回滚。

SQLite 表变更步骤参考：[SQLite 官方 ALTER TABLE 文档](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes)；PostgreSQL 事务内约束调整参考：[官方 ALTER TABLE 文档](https://www.postgresql.org/docs/current/sql-altertable.html)。

## 本地验收记录（2026-10-26）

已获授权后暂停本地后端，创建 `data/novelvids-before-project-name-scoping.db`（权限 `0600`），完成实际 SQLite 迁移并重启。迁移后、重启前逐表核对 32 张表的记录哈希与备份一致，7 个项目及 3307 个章节完整保留。旧库原有的五个非项目索引存在缺失条目，已定向 REINDEX，完整性检查为 `ok`，外键违规为零。重启时原初始化逻辑为两个无团队、无创建者的历史项目及其用量流水补齐了默认团队，书稿、章节、用量和金额保持不变。恢复该原始备份时应重新执行数据库完整性检查，对原有索引异常进行 REINDEX。
